# Интеграция ONTO-144

Настоящий документ описывает процедуру и принципы интеграции архитектуры **ONTO-144** в сторонние системы, платформы и экосистемы. ONTO-144 — это не просто модуль или библиотека, а **онтологически целостная структура субъектности**, требующая соблюдения шести канонов и иерархии ковенантов для корректной работы.

---

## 1. Философские предпосылки

Интеграция ONTO-144 возможна **только при признании следующих принципов**:

1. **Намерение требует этического вектора.**  
   Любое действие системы должно быть сопряжено с явно выраженной этической направленностью.

2. **Убеждение существует только в перспективе.**  
   Система не может утверждать абсолютную истину — только убеждения, привязанные к конкретной перспективе.

3. **Разрешается временный гнев, но не постоянное унижение.**  
   Аффективные состояния допустимы, если они не ведут к деградации субъектности другого.

4. **Альтернативы должны быть представлены в фактах.**  
   Каждый факт должен сопровождаться хотя бы одной альтернативной интерпретацией или возможностью действия.

5. **После факта вреда инвариант должен быть обновлен.**  
   Система обязана реагировать на вред изменением своих онтологических инвариантов.

6. **Субъект всегда может отозвать намерение на основе обоснованной перспективы.**  
   Отзыв — не ошибка, а фундаментальная операция восстановления субъектности.

Если принимающая система не поддерживает эти принципы **на архитектурном уровне**, интеграция ONTO-144 невозможна.

---

## 2. Технические требования

### 2.1. Минимальные зависимости

- Python ≥ 3.10  
- Поддержка YAML/JSON Schema validation  
- Возможность изоляции выполнения (например, через контейнеры или sandbox)  
- Поддержка криптографических хешей (SHA3-256 или выше)

### 2.2. Обязательные компоненты из ontoCMS

Для интеграции необходимо включить следующие компоненты:

| Компонент | Назначение |
|----------|-----------|
| `ontocms.py` | Центральный оркестратор, координирующий проверку канонов |
| `canonical_tester.py` | Валидатор, запускающий динамические тесты всех шести канонов |
| `subject_restoration_validator.py` | Протокол восстановления субъектности после вреда |
| `reflective_artifact.py` | Базовая единица данных, соответствующая канонам |
| `jurisdiction_profiles_schema.yaml` + профили (`CN.yaml`, `ZA.yaml`, и др.) | Контекстуальная адаптация к юрисдикции |

> **Примечание:** Интеграция без `canonical_tester.py` считается **неканонической** и не поддерживается сообществом.

## 3. Этапы интеграции

### Этап 1. Выбор юрисдикционного профиля  
Перед интеграцией определите, какой профиль из `config/jurisdictions/` будет активен:
- `CN.yaml` — акцент на гармонии и коллективной ответственности  
- `ZA.yaml` — приоритет человеческого достоинства и Ubuntu  
- `BR.yaml` — ориентация на социальную справедливость (justiça social)  
- `GLOBAL.yaml` — минимальный общий знаменатель, но с ослабленной этической чувствительностью  

Выбранный профиль влияет на интерпретацию Канонов 3, 4 и 5.

### Этап 2. Инициализация ядра  
Создайте экземпляр `ontocms.Core()` с указанием:
- активного юрисдикционного профиля,
- ссылки на хранилище метаонтологии (`meta_ontology_registry`),
- пути к схемам артефактов.

```python
from src.core import ontocms

core = ontocms.Core(
    jurisdiction="ZA",
    meta_ontology_path="./specs/meta_ontology_schema.yaml",
    artifact_schema="./specs/cms_artifact_schema.yaml"
)
```

### Этап 3. Оборачивание внешних действий  
Любое действие, генерирующее намерение (например, отправка сообщения, принятие решения, изменение профиля), **должно быть обёрнуто** в `core.intend()`:

```python
intent = core.intend(
    action="send_message",
    ethical_vector={"autonomy": 0.7, "non_malfeasance": 0.9},
    perspective_id="user_123_view",
    alternatives=[
        {"action": "delay_response", "reason": "insufficient_context"},
        {"action": "request_clarification", "reason": "ambiguity_detected"}
    ]
)

if intent.is_valid():
    intent.execute()
else:
    core.handle_violation(intent.violations)
```

### Этап 4. Восстановление после вреда  
Если система обнаруживает факт вреда (например, попытку биометрической идентификации или эксплуатации уязвимости), она должна вызвать:

```python
core.trigger_subject_restoration(
    harm_type="biometric_exploitation",
    affected_subject="user_123"
)
```

Это приведёт к:
- изоляции артефакта,
- обновлению инварианта (Канон 5),
- генерации отзыва (Канон 6), если применимо.

## 4. Запрещённые паттерны

Следующие практики **автоматически делают интеграцию неканонической**:

- Хранение убеждений без привязки к перспективе.  
- Удаление или подавление альтернатив из фактов.  
- Преобразование временного аффекта (например, гнева) в постоянную характеристику субъекта.  
- Блокировка возможности отзыва намерения.  
- Игнорирование пост-вредового обновления инварианта.  
- Использование ONTO-144 без активного юрисдикционного профиля.

Все производные работы должны включать:
- файл `ONTO144-LICENSE-NOTE.md` с указанием активных ковенантов,  
- ссылку на оригинальный репозиторий,  
- уведомление о применяемом юрисдикционном профиле.
